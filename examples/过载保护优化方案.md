# 背景

目前的过载保护方案，存在如下几个问题：

1. 使用请求耗时是否超过800ms的作为过载的条件之一，有可能会产生一些误报，因为请求耗时并不能真正标示过载，正常的业务请求耗时也可能会超过 800ms
2. 当出现过载时，会设定单位周期的最大请求量阈值，超过阈值的请求直接丢弃，有可能导致用户访问出现时好时坏的情况。
3. 每个周期的跨度太长（当前使用的是10s），有可能导致负载调整不够及时，请求量出现锯齿状波动，比较难贴合真实容量
4. 接入Svr保护自己的方式较为简单，是配置一个经验阈值，超过阈值的请求直接丢弃。而线上的请求变化较大，压测出来的阈值不一定适用线上请求。另外没有区分业务优先级，所有命令字同等对待，出现过载时，无法优先保证重要请求的正常访问。

综上，考虑对过载保护机制进行一些优化。

针对问题a，考虑使用被调服务是否出现排队（平均排队时间超过20ms） 来判断是否过载，因为排队可以真实反映一个服务的负载情况，出现了排队， 说明负载较高 针对问题b，考虑引入用户优先级概念；用户优先级根据用户id进行hash运 算得到，取值范围为[0,100), 值越小，优先级越大；当出现过载时，设置一个 合理的用户优先级阈值U，用户优先级值比U小的请求可以正常访问，值比U大 的请求丢弃，这样可以保证减载操作只会影响优先级值比U大的用户，值比U小 的用户不受影响。另外为了保证公平性，hash算法每一小时调整一次。 针对问题c，考虑将时间周期缩短为1秒，另外如果请求量超过1000，也认 为达到了一个周期，这样可以及时进行减载和加载操作，保证请求量平滑的贴 合真实容量。 针对问题d， 同样使用是否出现排队来判断是否过载，不过是判断的本地 队列。另外引入业务优先级的概念，业务优先级在接入层的命令字配置中指定 ，取值范围[0,10)，值越小，优先级越大。过载时，设定合理的业务优先级阈值 B, 业务优先级值比B小的请求可以正常访问，值比B大的请求丢弃，优先保证重 要的业务不受影响。另外只使用业务优先级的话，粒度太粗（相同优先级的请 求要么全部丢弃，要么全部接受），有可能导致优先级阈值在两个相邻值之间 来回切换，导致用户请求时好时坏。因此进一步结合用户优先级来进行控制， 细化优先级粒度：将每一个业务优先级扩展成100个小等级，每个小等级对应 一个用户优先级，这样总共支持10*100个小等级(如下图所示)，粒度变得足够 精细，减载也会变得足够平滑，另外也可以保证指定的用户请求要么都成功， 要么都失败。

# 根据排队情况判断过载

## 逻辑层返回排队时间

改造逻辑层框架，在命令字服务计算每个请求的排队时间, 并设置在 ResponseContext中，返回给接入层，伪代码如下： LogicServantImp::doCgiRequest(...) { taf::Int64 queue_time = TNOWMS - current->getRecvTime(); map<std::string, std::string> context = current->getResponseContext(); context["queue_time"] = L2S(queue_time); current->setResponseContext(context); ...

}

### 接入层统计排队时间

接入层收到排队信息后，统计平均排队时间： a． 从ResponseContext获取排队时间 b． 统计每个命令字每个周期的平均排队时间 c．根据平均排队时间判断是否过载 伪代码如下： LogicServantPrxCallback::callback_doCgiRequest(...) { ... // a. 从ResponseContext获取排队时间 const map<std::string, std::string> &response_context = this->getResponseContext(); map<std::string, std::string>::const_iterator it = response_context.find("queue_time"); if (it != response_context.end()) { taf::Int64 queue_time = S2L(it->second); // b. 统计每个命令字每个周期的平均排队时间 ... } ... } TCmdRunInfo::CheckOverload() { ... // c. 根据平均排队时间判断是否过载 if (平均排队时间超过20ms) { 认为过载 } ... }

# 使用用户优先级减载

### 用户优先级计算

user_ priority = hash (uin + str(current_timestamp/ 3600)) % 100

### 准入级别计算

准入级别由用户优先级B来标示，用户优先级值大于B的请求丢弃，用户优 先级值小于等于B的请求正常访问，B的计算规则如下：

1. 在每个周期统计每个用户优先级对应的接收请求数，形成一个请求量直方图（X轴为用户优先级，略掉了部分点）
2. 如果某个周期发生过载，则将下个周期的“期望请求量”下调α（5%），否则将期望请求量上升β（1%），假设计算得到的期望请求量为X
3. 根据期望请求量，确定用户优先级阈值：假设优先级阈值为U\*，则用户优先级0到用户优先级U\*的“上周期请求量”的和，需要刚好不超过X。如下图所示，假设X=400，而优先级 0到4的请求量之和是375, 优先级0到5的请求量之和是425，因此算的U\*=4

这个计算策略的优点，是可以和下面的“接入层自我保护”采用相同的算 法，而“接入层自我保护”使用此算法是十分必要的，详见后面说明。

### 减载策略

对于优先级值大于U*的请求，直接丢弃，小于等于U*请求，正常访问

# 被调的被调过载的场景

上面的过载保护, 只能保护直接被调的服务，考虑下面的场景：接入层调用 B，B调用C，如果B的容量比C大，并且请求量不是很大，则可能B不会出现排 队，但是C会出现排队，此时接入层并不了解C的排队情况，无法根据B的排队 情况判断C是否过载。不过此时接入层可以感知请求平均耗时较高，因此还是 要保留根据请求耗时判断过载的逻辑：设定请求耗时阈值T，当平均请求耗时 超过T时，认为过载，否则认为请求正常。 这里将请求耗时阈值设定为1000ms，原因如下：a. 逻辑层调用后端服务设 置的超时时间为3000ms，所以设定的阈值需要比3000ms低; b. 正常情况下， 我们的命令字最大耗时不会超过800ms, 命令字的平均耗时大概40ms，绝大部 分命令字耗时在100ms以内。

# 接入层自我保护

以上介绍的接入层保护后端的机制，接入层本身也会过载，也需要进行保 护。大致思路为：根据是否排队判断是否过载，使用业务优先级和用户优先级 作为准入级别来减载

### 业务优先级配置

业务优先级在命令字路由表中配置，如果不配，则默认优先级为9（最低优 先级）

### 准入级别计算

准入级别由业务优先级B和用户优先级U的组合来标示，记为（B，U），准 入级别计算规则如下：

1. 在每个周期统计每个（B，U）对应的接收请求数，形成一个请求量直方图（X轴为组合优先级，略掉了部分点）
2. 如果某个周期发生自身过载（接入层出现排队情况），则将下个周期的“期望请求量”下调α（5%），否则将期望请求量上升β（1%），假设计算得到的期望请求量为X
3. 根据期望请求量，确定用户优先级阈值：假设优先级阈值为(B\*,U\*)，则组合优先级(0,0) 到组合优先级(B\*,U\*)的“上周期请求量”之和，需要刚好不超过X，如下图所示，假设X=400 ，而优先级(0,0)到(0,4)的请求量之和是375, 优先级(0,0)到(0,5)的请求量之和是425，因此 (B\*,U\*)=(0,4)

这个策略的好处是：在发生过载时，减掉的是固定比例的请求量，若未发 生过载，上调的也是固定比例的请求量；而如果直接调整组合优先级级别

，无法保证增减的请求量比例是固定的（每一个级别的请求量并不均匀） ，定位到一个合适的级别需要较长周期。

### 减载策略

对于优先级值大于(B*,U*)的请求，直接丢弃，小于等于(B*,U*)请求，正常 访问

# 总结

### 保护后端

- 根据排队时间，可以真实有效的感知服务的负载情况

b．由于接入层只能感知逻辑层的排队情况，无法感知逻辑层后端的排队情 况。所以接入层在没有感知到排队的时候，还需要根据请求耗时来判断过载。

- 引入用户优先级，避免用户访问出现时好时坏的情况。

### 保护自己

1. 使用接入层自身的排队时间作为过载依据
2. 使用业务优先级和用户优先级的组合作为准入级别，出现过载时，优先保证重要业务的访问，另外也保证用户访问不会出现时好时坏的情况
3. 使用直方图机制，确保每次减载和加载的量足够均匀。

### 和微信区别

- 微信在每一层都做了保护，而我们只在接入层保护直接被调的逻辑层和接入层自身（受限于taf框架，对每一层进行改造的成本比较大：需要在taf框架内透传优先级，并计算过载情况，决定请求是否丢弃，并回传过载情况给调用方；调用方需要根据后端的负载，决定是否发送请求；另外改造后升级taf版本也会比较麻烦）
- 微信统计的是每一个服务节点的负载，没有细化到命令字，而我们统计的是每一个命令字的负载，没有区分服务IP（同样受限于taf框架，taf框架的rpc 调用，屏蔽了IP信息，如果要改造的话，也需要改造taf框架）；
- 微信是在被调的服务统计负载，而我们是在主调的服务（接入层）统计负载；不过我们接入层保护自己的逻辑和微信的逻辑比较类似；
- 我们认为同一个逻辑Svr的的所有命令字的业务优先级是相同的，因此只使用用户优先级作为准入级别；而微信由于保护了后端的后端，而后端的后端可能会收到不同业务优先级的请求，因此准入级别考虑了业务优先级。当然我们接入层的自我保护，是考虑了业务优先级的

### 遗留问题

1. 多个接入层节点，对某个命令字计算得到的用户优先级阈值，可能会不一样，因此用户访问也会出现时好时坏的情况，不过情况比不使用用户优先级要好。微信也有类似问题，同一个服务的不同节点，过载情况也是不一样的，可能也会出现此种情况（不清楚微信是否根据负载进行了负载均衡）
2. 对后端的后端的保护，不够准确和及时
3. 由于没有在taf框架内计算排队时间， 只是在业务函数LogicServantImp::doCgiRequest 中计算排队时间，因此如果请求出现了异常（譬如排队时间超过主调超时时间），执行流没有进入到业务函数，就无法统计到排队时间。
